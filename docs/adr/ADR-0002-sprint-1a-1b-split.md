# ADR-0002: Sprint 1A (収集) と 1B (LLM/台本) を分割する

- 日付: 2026-05-28
- ステータス: Accepted
- 決定者: 人間 + アーキテクト
- 関連: [requirements-v1.0.md](../requirements-v1.0.md) §15, DL-003

## 背景

「収集が不安定」かつ「LLM 出力品質が不安定」という2つの不確実性を同時に検証すると、どちらが原因で番組が出ないのか切り分けできなくなる。

## 決定

- **Sprint 1A**: ソース取得 → SQLite 保存 → Discord 収集サマリーまで。LLM / TTS / 動画 / YouTube は **一切実装しない**。
- **Sprint 1B**: MiMo / DeepSeek を使ったトピック選定・台本生成。音声化はまだ。
- 1A の DoD (要件 §15.1) を満たすまで 1B には進まない。

## 根拠

- 収集の不安定要因 (RSSHub ルート、Cookie、海外IP、feedparser bozo) を確定させてから LLM のプロンプト調整に入る方が、A/B/C 比較の前提が安定する。
- 1A 完了時点で「収集さえできれば毎日 Discord にニュースが流れる」状態になり、これだけでも個人的価値が出る。番組化は段階的に積み上げ可能。
- 個人運用の認知負荷上限内に各スプリントを収める (5-10日 / 5-7日)。

## 影響

- Sprint 1A コード内で LLM 抽象化レイヤーや TTS インターフェースを **前もって作らない**。実装時に必要になってから作る (YAGNI)。
- `config/llm_profiles.yaml` のスキーマだけは Sprint 1A の YAML ローダ実装時に用意してよいが、`collect` パイプラインから参照しない。
- ドキュメント上の「Sprint 1A スコープ外」リスト (DESIGN.md §9) を実装者・レビュアー両方が監視する。

## 不採用案

- **一括実装**: 1A + 1B を同時に進める → 不確実性の分離不可、巻き戻し時のコスト大。
- **TTSも同時導入**: TTS は Sprint 2 まで触らない。理由は Irodori-TTS の漢字読み精度問題と読み仮名辞書整備のオーバーヘッドが Sprint 1B の本筋から逸れるため。
