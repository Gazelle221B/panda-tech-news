- 日付: 2026-08-01
- ブランチ: `agent/T58-asr-gate-impl`
- 実装者: Claude Code
- 参照: [Issue #54](https://github.com/Gazelle221B/panda-tech-news/issues/54)

## 背景

参照音声条件付け TTS (Irodori 等) は確率的に台本外の発話 (幻話/babble) を挿入することが
実測されている (2026-07-31 dry-run 観測: 幻話は「文頭・文末への一言追加」として現れ、文の
中身自体は台本どおりだった)。文単位合成の直後にローカル ASR (Whisper) で書き起こしを取り、
期待文と突き合わせることで、この手の混入を機械的に検出する。

## 変更内容

### 1. 新規 `src/karyu_tech_news/tts/asr_gate.py`

- `AsrBackend` (Protocol, `transcribe(wav_bytes: bytes) -> str`) で ASR 実装を抽象化。
- `WhisperAsrBackend`: `openai-whisper` をメソッド内で遅延 import (`kokoro.py` の
  `KokoroTTSEngine._backend()` と同じ流儀)。未導入なら `AsrUnavailableError`。モデルは
  初回 `transcribe` でロードしインスタンスへキャッシュ (既定 `model_name="turbo"`)。wav
  bytes は一時ファイル経由で `model.transcribe(path, language="ja", temperature=0.0)`。
- `verify_sentence(expected, transcript) -> AsrVerdict`: 正規化 (小文字化・空白/句読点除去)
  した上で `difflib.SequenceMatcher.ratio()` (類似度) と長さ比 (書き起こし/期待文) を計算。
  - 類似度 < 0.5 → `mismatch` (文が丸ごと別物)。
  - 類似度 >= 0.5 かつ長さ比 > 1.6 → `insertion` (幻話疑い)。
  - それ以外 → `ok`。
  - 閾値の実測根拠と「かな/漢字/ローマ字表記ゆれ・数字誤読は対象外 (将来課題)」を docstring
    に明記。
- `AsrVerdict` は frozen dataclass (`status: Literal["ok","mismatch","insertion"]`,
  `similarity: float`, `length_ratio: float`)。

### 2. `src/karyu_tech_news/tts/engine.py`

`SynthesisResult` に `asr_retried_sentences: int = 0` / `asr_failed_sentences: int = 0` を
追加 (個別エンジンは既定値のまま、`synthesize_script()` が集約する既存パターンを踏襲)。

### 3. `src/karyu_tech_news/tts/synthesize.py`

`synthesize_script()` に `asr_backend: AsrBackend | None = None`,
`asr_max_retries: int = 2` を追加。既存の機械的品質チェック (有音率など) を通過した文のみ
ASR 検証対象にする。期待文には **絵文字注釈前の `sentence`** を使う (絵文字はスタイル制御
トークンで発話されないため、比較に混ぜると類似度が不当に下がるのを避けるため)。

- verdict が `ok` 以外 → 同じ `text` (絵文字注釈込み) で再合成し、最大 `asr_max_retries`
  回リトライ。リトライ後の音声も機械的品質チェック (`analyze_wav_signal`) を通した上で
  ASR 再検証する。
- リトライで `ok` になった文 → その音声を採用し `asr_retried_sentences` を加算。
- リトライ上限まで解消しない文 → 従来の fail-open と同様に `skipped_sentences` へ計上し
  `asr_failed_sentences` を加算 (chunk は結合対象に含めない)。既存の produce 側
  「skipped_sentences>0 で mp3 生成を中止」がそのまま fail-fast として効く。
- `asr_backend=None` (既定) なら ASR 経路を一切呼ばない (後方互換)。
- `AsrUnavailableError` はここで捕まえず呼び出し元へ伝播させる (仕様どおり)。

### 4. `src/karyu_tech_news/main.py` produce

- persona `tts` ブロックの新キー `asr_gate` (bool, 既定 false) を読む。
  **読み辞書ロード部 (`reading_path` 周辺) には触れていない** — T56 (PR #55) との
  コンフリクトを避けるため、`caption` の読み込み行の直後に 1 行追加するに留めた。
- `asr_gate: true` なら `WhisperAsrBackend()` を構築して `synthesize_script` に渡す
  (構築自体は whisper 未導入でも安全)。`AsrUnavailableError` が
  `synthesize_script` から伝播した場合は ERROR ログを出して `exit(1)` (fail-fast。
  有効化した品質保証を黙って無効化しない)。
- 合成後、`synth.asr_retried_sentences > 0` なら件数を `typer.echo` で出力。

### 5. `config/hal_persona.yaml`

`tts.asr_gate: false` を用途コメント付きで追記 (既定は明示的に無効)。

### 6. `pyproject.toml` / `uv.lock`

optional extra `qa-asr = ["openai-whisper>=20250625"]` を追加 (`tts` extra とは分離、
dev group には入れない = CI を重くしない)。`whisper` モジュール向け mypy override
(`ignore_missing_imports = true`, `kokoro_onnx`/`pydub` と同じ流儀) を追加。`uv lock` で
lock ファイルを更新済み。

## テスト (whisper 実体は使わない。fake backend を注入)

- `tests/test_tts_asr_gate.py` (新規, 11 件): `verify_sentence` の ok/mismatch/insertion/
  空 transcript/表記ゆれ (「AI」↔「エーアイ」)/大小文字・句読点無視、`AsrVerdict` が
  frozen であること、fake backend が `AsrBackend` プロトコルを満たすこと、
  `WhisperAsrBackend` の未導入時 `AsrUnavailableError` (構築自体は落ちない) とモデル
  キャッシュ (`load_model` が初回のみ呼ばれる)。
- `tests/test_tts_synthesize.py` (追加 6 件): asr_backend 未指定時に ASR 経路
  (`verify_sentence`) が一切呼ばれないこと、全文 ok なら従来 (asr_backend なし) と音声・
  カウンタが一致すること、1 文が insertion → リトライで ok になり
  `asr_retried_sentences == 1`、リトライ上限 (既定 2 回) まで解消しない文は
  `skipped_sentences`/`asr_failed_sentences` に計上、`asr_max_retries=0` でリトライ
  無効化を尊重すること、`AsrUnavailableError` が握りつぶされず伝播すること。
- `tests/test_produce_pipeline.py` (追加 4 件): `asr_gate` 未設定/明示 false で
  `WhisperAsrBackend` が構築されないこと、`asr_gate: true` で構築されること、有効化した
  のに ASR 利用不能なら ERROR + exit 1 になること。zero-frame エンジンで ASR 到達前に
  fail する既存経路と、ASR まで到達させるための強振幅 (`\xff\x7f`) wav ヘルパーを使い分けた
  (`_wav_bytes` の弱振幅 `\x01\x00` は無音判定閾値以下で ASR 到達前に skip されるため)。

## 仕様から外れた判断・不確かな点

- **`asr_retried_sentences` / `asr_failed_sentences` の意味付け**: チケット仕様は
  「集計する」とだけ書かれており、リトライ回数の合計かリトライが必要だった文数かは
  明記されていなかった。本実装では **「リトライして最終的に ok になった文の数」を
  `asr_retried_sentences`、「リトライ上限まで解消せず skip になった文の数」を
  `asr_failed_sentences`** とした (どちらも文数ベース、リトライ試行回数の合計ではない)。
  チケット記載の統合テスト例 「1文が insertion → リトライで ok になり
  asr_retried_sentences=1」と整合する解釈。
- **リトライ時も機械的品質チェックを再適用**: チケットには明記がなかったが、再合成した
  音声が万一壊れていた場合にそれを ASR 検証してしまう (whisper は wav 破損に寛容な場合が
  あり誤って ok 判定しかねない) のを避けるため、リトライ音声にも `analyze_wav_signal`
  (valid_wav / has_pcm_signal) を通してから ASR 検証する設計にした。
- **ASR 比較に使う期待文は絵文字注釈前の `sentence`**: `text` (絵文字注釈込み) を engine
  へ渡す一方、ASR との比較は注釈前のプレーンな文で行う。絵文字はスタイル制御用トークンで
  発話されないため、比較に含めると表記ゆれとは別の理由で類似度が不当に下がると判断した
  (design には明記がなかったための実装判断)。
- **`WhisperAsrBackend` の `model_name` 既定 "turbo"**: チケット記載どおり。実運用での
  精度・速度トレードオフの確定は人間の試聴判断が必要 (T32 話速調整と同様、実 whisper
  環境での smoke は本チケットの範囲外)。
