## Codex レビュー指摘対応 (2026-07-12)

PR #25 に対する Codex 独立レビューの指摘 5 件 (High 1 / Medium 3 / Low 1) を同一ブランチで反映した。

1. **[High] upload URL の origin 検証** (`youtube.py` `_validate_upload_location`): resumable
   upload initiate 応答の `Location` ヘッダを無条件に信頼せず、Bearer token 付き PUT を送る前に
   scheme=https かつ host が `googleapis.com` (完全一致 or サブドメイン) であることを確認するよう
   にした。不合格時は `YouTubeError` (メッセージには host のみを含め URL 全体は含めない)。回帰
   テスト: 悪性 host (`evil-googleapis.com`) / http スキームの 2 パターンで PUT が一切送られない
   ことを検証。
2. **[Medium] 例外メッセージの応答本文 redaction** (`youtube.py` `_error_detail`): レスポンス本文
   をそのまま含めていたのをやめ、JSON らしき本文からは安全キー (`error` / `error_description`、
   Google API の `{"error": {"message": ...}}` 形式も対応) の値のみを抽出するよう書き換えた。非
   JSON 本文や安全キーが無い本文は `HTTP <status> (content-type=...)` のみに留める。回帰テスト:
   本文中の `access_token` 等の非安全キーやトークン値が例外メッセージへ反射しないことを検証。
3. **[Medium] resumable upload の再開・リトライ** (`youtube.py` `_upload_bytes` /
   `_query_upload_offset` / `_put_range`): PUT が接続失敗または 5xx の場合、Google resumable
   protocol に従い `Content-Range: bytes */<size>` の空 PUT で再開位置を照会し (308 → `Range`
   ヘッダから offset 取得、200/201 → 完了扱い)、残りバイトのみを `Content-Range: bytes
   <start>-<end>/<size>` で再送する。4xx は再開不能として即 fail-fast。リトライ上限は
   `MAX_UPLOAD_RETRIES = 2` (FR-013 に合わせ最大2回、初回 + リトライ2回で計3回試行)。回帰テスト:
   (a) 503→308 再開→成功、(b) 3回連続失敗で `YouTubeError`、(c) 再開位置照会が 404 で即 fail の
   3 パターン。既存の `test_upload_video_success` / `test_upload_video_put_fails` は新しい
   Location 検証・Content-Range 形式に合わせて更新。
4. **[Medium] T41 daily_pipeline.sh 契約テスト追加** (新規 `tests/test_daily_pipeline.py`): fake
   `uv` シェルスタブ (`KARYU_UV` で差し替え) を使い `scripts/daily_pipeline.sh` を実サブプロセス
   として起動する契約テストを 3 件追加。(a) `PUBLISH_YOUTUBE` 未設定 (既定) では publish 段が
   呼ばれない、(b) `PUBLISH_YOUTUBE=1` でも produce が非 0 なら publish は実行されず全体 rc が
   produce の rc になる、(c) `PUBLISH_YOUTUBE=1` で publish が非 0 なら全体 rc へ伝播する。
   Irodori サーバ起動は `KARYU_HEALTH_URL` を `file://` の既存ファイルに向けて「既に稼働中」判定
   させ回避 (`test_produce_pipeline.py` の既存 daily_pipeline smoke と同じ手法)。3 テストとも
   1〜2 秒程度で完走。
5. **[Low] IMPLEMENTATION_PLAN-3.md の DoD を ADR-0008 へ同期**: T41 行の「PROJECT_STATE /
   TEST_LOG」への言及を「`docs/test-logs/` のチケットログ + PR 本文へ記録 (ADR-0008)。
   `PROJECT_STATE.md` はマージ後 docs ブランチで更新」に書き換えた。

### 保守側に倒した判断

- `_upload_bytes` の再開位置照会 (`_query_upload_offset`) 自体が失敗した場合 (接続失敗 / 200・
  201・308 以外の応答) は、追加リトライをせず即座に `YouTubeError` にしている。FR-013 の
  「最大2回リトライ」はデータ送信そのものに適用し、照会の失敗は再開不能とみなすシンプルな設計
  にした (照会自体をリトライすると上限管理が複雑化するため)。
- `daily_pipeline.sh` の `notify_failure()` は `label` 引数を受け取るが、成功時ログ
  (`log "produce 失敗通知: 処理完了"`) が `produce` 固定文言で `publish` 失敗時にもそのまま
  出力される既存の軽微な表示バグを発見した。今回の 5 件のスコープ外のため修正しておらず、
  `test_publish_failure_propagates_return_code` はこの文言に依存しない `Discord alert: sent`
  / `WARNING: publish 失敗 (rc=9)` を検証対象にした。
