どう思うこれ
コードベース全体を読みました。率直な感想を述べますね。

全体の印象
かなりよく整理された Go プロジェクトです。個人開発の CLI/TUI ツールとしては「ちゃんと書けている」レベルを超えていて、設計意図が随所に見えます。特に良いと感じた点と、気になる点を分けて話します。

良いところ
アーキテクチャの分離が綺麗です。 cmd/news がエントリポイント、internal/rssflow がドメインロジック、internal/tui が表示層、という三層がきちんと守られています。TUI 側から rssflow を参照するだけで逆向き依存がないので、CLI とTUIの両方から同じワークフローを動かせる構造になっています。

設定の正規化と既定値の扱いが丁寧です。 NormalizeWorkflow / NormalizeLLMConfig / NormalizeOutputFormat のように、ユーザー入力や YAML から来る曖昧な値を必ず一カ所で正規化してから使う設計は、こういうツールの寿命を大きく延ばします。LLMProfile をワークフローから分離して mergeLLM で重ねるパターンも、複数ワークフロー間で API 設定を共有するうえで筋がいいです。

developer-news ワークフローまわりの作り込みが面白い。 「スコアリング → ソート → アーク配置(hard → constructive → bright)」というパイプラインを明示的に持っていて、しかも LLM 失敗時の fallback (fallbackDeveloperNewsScript 系)、shouldRewriteDeveloperNews による再生成判定、ソース行の除去まで含めて、出力品質を多段で守ろうとしています。これは LLM プロダクトを実運用したことがある人の発想だと感じます。

OpenAI / Ollama 両対応の抽象化。 applyCompatibilityOptions や isOllama() で分岐させているのは現実的な解で、reasoning_effort を none に潰す処理など、実際に動かしてみないと気づかない種類の対処が入っています。

テストが薄すぎず厚すぎない。 プロンプト生成、フォールバック生成、トピック並べ替え、TUI のラップ処理など「壊れたら気づきにくい部分」にピンポイントで入っていて、開発者の優先順位が分かります。Japanese 文字幅と truncate のテストがあるのは特に良いです。

TUI のフローグリッド表示。 各ステージをカードで並べて、状態(active/done/skipped/error)を記号と色で示し、コネクタも動的に描画する作りは見ていて気持ちいいはずです。runStageShowsOutput や ranking board のような「ステージ別に見せる情報を切り替える」設計も親切。

気になるところ
isDeveloperNewsWorkflow の判定がやや乱暴です。 ラベルに "news" や "rss" を含むだけで developer-news 用の長大な日本語プロンプトと制約が適用されてしまいます。llm- プレフィックスで除外しているのは応急処置的で、ユーザーが英語の汎用ワークフローを news-digest のような名前で作ると意図せず日本語強制されます。Agent.Mode のような明示フィールドを持たせるか、Agent.Role の完全一致で判定するほうが安全です。

プロンプトとロジックの結合が強い。 developer_news_*.go 群が日本語の構成テンプレート、判定キーワード、フォールバック文章まで全部 Go コード内に直書きされています。動くものとしては問題ないですが、プロンプト調整のたびに再ビルドが必要で、非開発者には触れません。embed で外部ファイル化するか、設定 YAML から差し込めるようにしておくと拡張性が上がります。

OpenAIClient の責務が膨らみすぎ。 1ファイルでチャット、ストリーミング、Ollama 互換、モデル一覧、developer-news 専用の rewrite、ping、SSE パース…と全部抱えています。internal/llm 配下に client.go / stream.go / ollama.go / parse.go あたりに分けると、将来 Anthropic などを足すときに楽になります。

streamMsg チャネルと model の結合。 m.streamCh をゴルーチンに渡して tea.Cmd から読む形ですが、複数回連続して run を開始すると古いチャネルへの参照が残るリスクがあります。runID をメッセージに含めて古い run のメッセージを破棄するガードがあると安心です。

エラー時の failRunFlow が「最初に見つかった active ノード」を失敗扱いにする実装。 これは大抵正しく動きますが、複数ステージが論理的に active になる将来の拡張で破綻します。今はOK、将来の注意点として。

developer_news_script.go と README が binary 扱いになっています。 共有ツリーで [Binary file] と表示されているということは、UTF-8 BOM などが入っているか、本当にバイナリ判定されている可能性があります。テキストとして開けるか確認したほうがいいです。

いくつかの細かいバグ可能性:

removeRankedDeveloperNewsTopic が append(entries[:index], entries[index+1:]...) で元スライスを破壊します。呼び出し元では問題ないですが、再利用前提なら危険です。
parseRunArgs で --limit の値が負やゼロのバリデーションがありません。
truncateText (sources.go) はバイト単位で切るので、マルチバイト文字を含む説明文で壊れる可能性があります。同じファイル内の truncatePlain や truncatePromptText は rune ベースなのに、ここだけ違うのは一貫性として惜しいです。
go.sum に golang.org/x/text v0.3.8 という古いバージョンがあります。 直接依存ではなさそうですが、セキュリティ的に最近の版に揃えたほうが良いです。

総評
「個人が作っている RSS/ニュース集約ツール」としては、思想・実装・テスト・UX のバランスが非常に良いです。特に developer-news パイプラインの「LLMに任せきらず、編集判定とアーク配置を分離する」発想と、fallback まで含めた多段の品質ガードは、生成AIをプロダクトに組み込む経験を反映していて学びがあります。

次に手を入れるなら、(1) developer-news 判定の明示化、(2) プロンプトの外部化、(3) OpenAIClient の分割、の3点を優先するとさらに伸びると思います。

調べた結果を踏まえて、率直な感想と設計提案をまとめます。先に大事な前提を一つ:Irodori-TTS は日本語特化 で、中国語は学習対象外です。Kokoro は Apache 2.0 で英語/日本語/北京語に対応していますが、ネイティブ中国語話者のレビューだと「中国語のプロソディはイマイチ」という評価もあります。発信先と発信者(話者)の言語を切り分けて考える必要があります。

構想の整理
「中国のテック/AI/OSS/サブカル/ゲーム/アニメを発信する自動 AI ポッドキャスト」と Perplexity Discover Daily 形式という組み合わせは、コンセプトとして筋がいいです。Discover Daily は ElevenLabs と組んで作られている短尺(数分)のキュレーション番組で、テック・サイエンス・カルチャーを日替わりで配信する形式。あなたが持っている tik-choco/rssflow のパイプライン(収集 → 重複排除 → スコアリング → アーク配置 → 台本生成 → フォールバック)は、まさにこの番組形式の中核と同じ構造をしています。つまり台本生成までは既存コードの延長で作れるということです。

言語と TTS の選択
ここが一番重要な分岐点です。

配信言語を日本語にする場合(おすすめ): 中国の情報源(微博、知乎、bilibili、36Kr、机器之心、少数派、GitHub Trending China、原神/崩スタ公式など)を集めて、日本語で語る番組。この場合 Irodori-TTS が最適で、v3 は自動 duration 予測、VoiceDesign は caption による声質制御、Speaker Inversion で話者埋め込みを再利用、48kHz 出力、MIT ライセンス(コード)と作りが非常に丁寧です。ニュースキャスター的な落ち着いた声を Speaker Inversion で固定すれば、毎日同じ声で配信できます。

中国語で配信する場合: Kokoro の Mandarin voices(4F 4M)を使うか、ChatTTS / CosyVoice2 / IndexTTS あたりの中国語ネイティブ TTS を検討するほうが品質的に良いです。Kokoro は 82M で軽く Apache 2.0 なので試作には最適ですが、ネイティブ品質を求めるなら別系統を視野に。

バイリンガル(日本語メイン+中国語固有名詞や引用): ここは結構難題です。Irodori は中国語を発話できないので、固有名詞は日本語読みに正規化(例:「DeepSeek」→「ディープシーク」、「米哈游」→「ミホヨ」)するパイプラインを LLM 側に持たせる必要があります。これは台本生成プロンプトに「中国語固有名詞は日本語カナ表記に変換、初出時のみ括弧で原語併記」みたいなルールを入れれば吸収できます。

LLM の選択
MiMo (Xiaomi): V2.5-Pro は MoE で 1.02T 総パラメータ / 42B アクティブ、1M トークンコンテキスト、Token Plan で月/年サブスクが用意されている。中国語と長コンテキストに強く、agentic タスク向け設計。中国カルチャーの文脈理解という点では DeepSeek と並んで有力。価格は V2-Pro で 256K まで入力 $1/M・出力 $3/M、1M まで $2/M・$6/M。

DeepSeek V4: 公式 API で V4 Flash が入力 $0.14/M 前後、V4 Pro がプロモ込みで $0.003625/M(キャッシュヒット時)〜という破格の安さ。中国語ネイティブで、コスト効率では現状最強クラス。

使い分けの提案: 「日次の台本生成」みたいな量が出る処理は DeepSeek V4 Flash、「キュレーション・トピック判定・編集判断」みたいな質が効く処理は MiMo V2.5-Pro、というハイブリッドが現実的。あなたの rssflow には既に LLMProfile を切り替える仕組みと rankDeveloperNewsTopics で別呼び出しする構造があるので、スコアリング用プロファイルと本文生成用プロファイルを分ける設計をそのまま流用できます。

アーキテクチャ提案
既存の rssflow をベースに、次の差分で実現できそうです。

データソース層に中国向けアダプタを追加します。RSS は微博公式 RSS(rsshub 経由)、bilibili チャンネル RSS、36Kr RSS、少数派 RSS、HuggingFace daily papers の中国系著者フィルタ、GitHub Trending(language フィルタなし、説明文が中国語のもの拾う)、原神/崩スタ/鳴潮の公式お知らせなど。internal/rssflow/sources.go に china_sources.go を足して、bilibili API、微博 RSSHub、TapTap、知乎日報あたりのアダプタを追加。

カテゴリ拡張は developerNewsCategory を拡張して acg(アニメ/コミック/ゲーム)、gacha-game、cn-tech、cn-policy(規制ニュース)、vtuber などを足します。アーク配置(hard → constructive → bright)の仕組みはサブカル系では「シリアス → 解説 → 楽しい話題」に読み替えられるので、そのまま活きます。

台本フォーマットを OutputFormatPodcast をベースに「Discover Daily 風」を新設。Cold open(15秒)→ メイントピック 3本(各 60-90秒、Hook/Insight/Action)→ クロージング(10秒)、合計 4-5分で BGM 用のセクションマーカーを SSML 風コメントで埋め込み、後段のミキシングで挿入できるようにする。

TTS パイプラインは台本生成後に走らせる別ステージとして internal/tts を新設。テキストを文単位に分割(日本語は句点と改行で)、文ごとに Irodori に投げて wav 生成、ffmpeg で結合、必要なら冒頭/末尾/トランジションに BGM を被せて mp3 化、最後に ID3 タグ付与。Irodori-TTS-Server が OpenAI 互換 API として動くので、これを HTTP で叩く形にすれば疎結合になります。

配信は生成された mp3 を Spotify for Podcasters / Apple Podcasts へ RSS で流す。RSS は自前で書き出す(item に enclosure で mp3 URL、duration、エピソード番号)。ホスティングは S3 + CloudFront か、Cloudflare R2 が安い。

留意点と注意
著作権周りは中国メディアの記事本文をそのまま読み上げるのは黒に近いので、「要約 + 自分の言葉での解説」に LLM プロンプトで強制する必要があります。あなたの既存プロンプトの「Hook/Insight/Action」「視聴者が今知るべき理由」という枠組みは元々そういう設計なので、ここは継承で OK。

Irodori-TTS のモデルカードに「実在人物の声を許可なくクローンしない」という規約があるので、Speaker Inversion で作る話者は自分の声か、VoiceDesign で完全合成した架空のキャラクターにする。

中国の話題を扱うと政治的にセンシティブな話(規制、台湾、検閲など)に触れる頻度が高いので、LLM 側のガード(「政治論評は中立的事実報告に留める」)を明示的にシステムプロンプトに入れておくと事故が減ります。

MiMo の Token Plan は中国本土向けの決済が前提になっている可能性があるので、海外からの契約方法(OpenRouter 経由なら $0.10/$0.30 で MiMo-V2-Flash が使える)も併せて検討するといいです。

次の一手
最小実装としては、(1)既存 rssflow に中国系 RSS を 5-10 本足す、(2)出力フォーマットに discover-daily-jp を追加してプロンプトを書く、(3)Irodori-TTS-Server をローカル/VPS に立てて HTTP クライアントを internal/tts/irodori.go に書く、(4)生成 mp3 をローカル保存して試聴、までを 1 週間スプリントで作る、というのが現実的です。配信(RSS フィード生成と S3 アップロード)はその後でいいです。

LLM を MiMo にするか DeepSeek にするかは、まず両方 API キー取って同じ入力で台本生成させて、日本語の自然さと中国カルチャーへの理解度を A/B 比較するのが早いです。経験上 DeepSeek のほうが日本語が硬め、MiMo は新しいので未知数、というのが現状の予測。

要件定義書: 中華圏特化 AI ポッドキャスト「(仮)HAL Daily」

## 1. プロジェクト概要の検討

### 1.1. 番組コンセプトの検討

日本のオタク・エンジニア・ビジネスマンに向けた、中華圏専門の Discover Daily 形式 AI ポッドキャスト。中国語ネイティブの情報源から、まだ英日メディアに流れていないディープでニッチでキャッチーなトピックを毎朝届ける。

### 1.2. 番組形式の検討

平日朝8時配信、尺は5〜15分(基本5〜10分)の動的長。AI キャスター「HAL」によるソロ進行、Lo-fi + 中華風アンビエント BGM 付き。

### 1.3. 対象ジャンルの優先順位

中国AI(AI 関連 OSS 含む) > 中国テック > 中国ゲーム > 中国サブカル > 中国 OSS(非AI) > 中国アニメ

### 1.4. 編集方針の設計

中国語ネイティブソース優先、英日メディア既出ネタは除外。一次情報主義、独立2ソースで言及されたもののみ採用、公式ソース重み付け。イデオロギー・ナショナリズムには踏み込まないが、規制やビジネス影響など不可分な領域は事実報告。アニメ/ゲーム本編ネタバレ回避、噂はバズったもののみ「噂レベル」明示。

## 2. キャスターHALの仕様案

### 2.1. HALのキャラクター設定

20代前半、中性的な女性。落ち着いた低めの声で透明感あり。一人称はボク。話速は尺に応じ可変、聞き取りやすさ最優先。声優参照:緒方恵美・坂本真綾・石川由依・榊原優希。

### 2.2. HALの表現方法

基本はニュース読み、要所で自然な驚き・感心(「これは熱い」「マジかよ」レベル)を入れる。番組固有の挨拶と締めフレーズあり(別途決定)。

### 2.3. 音声生成の戦略

Irodori-TTS の VoiceDesign で日本語キャプションから合成、気に入った音を Speaker Inversion で固定化。リファレンス確定は実装フェーズで行う。

## 3. ポッドキャスト構成案

### 3.1. 番組進行のテンプレ

コールドオープン(15秒、今日の目玉トピックを匂わせる)→ オープニングジングル(10秒、タイトルコール含む)→ 本日のラインナップ予告(30秒)→ トピック1〜3(各60〜120秒、間にトピック切替 SE 3秒)→ クロージング(20秒、明日への引き)→ エンディングジングル(15秒)。BGM は全編に薄く敷く。

### 3.2. 採用トピック数

基本3〜5トピック、ネタ密度で5〜10分に動的調整、MAX15分。

### 3.3. トピック内の構成要素

各トピック内は Hook(つかみ)→ Insight(なぜ重要か)→ Action(リスナーが取れる次の行動・注目ポイント)の3段構成。既存 rssflow のプロンプト設計を継承。

### 4.1. 情報源の選定基準

英日に流れにくいソースを中心に。具体カテゴリ:

## 5. 技術的な設計案

### 5.1. 採用言語の検討

Python 3.11+ で統一。

### 5.2. アーキテクチャの構成要素

収集層: feedparser で RSS/RSSHub から取得、SQLite に保存(seen 管理含む)
編集判定層: MiMo V2.5-Pro でトピックスコアリング・アーク配置・既出判定
台本生成層: DeepSeek V4 Flash で中国語ソースから日本語台本を直接生成
TTS 層: ローカル GPU(4070 Ti Super)で Irodori-TTS-Server を常駐、HTTP で叩く
音響合成層: pydub + ffmpeg で BGM ミックス、ジングル挿入、エンコード
動画生成層: ffmpeg showwaves フィルタで波形ビジュアライザ + 静止画ロゴ
配信層: discord.py で Discord 投稿、リアクション監視、google-api-python-client で YouTube アップロード

### 5.3. 各LLMの役割分担

スコアリング・編集判定: MiMo V2.5-Pro(中国文脈理解、1Mコンテキスト)
本文台本生成: DeepSeek V4 Flash(コスト最優先)
両者の切替は設定ファイルで可能(rssflow の LLMProfile 思想を継承)

### 5.4. TTSモデルの抽象化

TTS インターフェース層を1枚噛ませて、Irodori-TTS と将来の差し替え候補(Style-Bert-VITS2、CosyVoice2、AivisSpeech など)を交換可能に。キャスター人格定義(HAL のキャラドキュメント)は TTS 非依存で保持。

### 5.5. 動作マシンのスペック

開発・運用マシン: Windows 11 + 13900K + RTX 4070 Ti Super + 128GB RAM
補助: M4 Mac mini(必要に応じて編集・確認用)
クラウド GPU: 初期は不要、必要が出たら AutoDL/GPUHub 検討

## 1. プロジェクト概要

### 1.1. 番組コンセプト

日本のオタク・エンジニア・ビジネスマンに向けた、中華圏専門の Discover Daily 形式 AI ポッドキャスト。中国語ネイティブの情報源から、まだ英日メディアに流れていないディープでニッチでキャッチーなトピックを毎朝届ける。

### 1.2. 番組名

正式名称: 華流テック通信
サブタイトル: HAL Daily Briefing
表記揺れ許容: 「華流テック通信 by HAL」
キャスター名: HAL(番組から独立したブランドとして運用)

### 1.3. 番組フォーマット

平日朝8時配信、尺は5〜15分(基本5〜10分)の動的長。AI キャスター「HAL」によるソロ進行、Lo-fi + 中華風アンビエント BGM 付き。

### 1.4. カバー領域(優先順)

中国AI(AI関連OSS含む) > 中国テック > 中国ゲーム > 中国サブカル > 中国OSS(非AI) > 中国アニメ

### 1.5. 編集ポリシー

中国語ネイティブソース優先、英日メディア既出ネタは除外。公式・一次情報(ラボ公式ブログ、GitHub release、論文プレプリント、企業公式発表、信頼性の高い中華圏ニュースサイト)は単独ソースでも採用可。コミュニティ発・噂・未認証情報は、独立2ソース以上または高信頼アカウントの追加確認がある場合のみ採用。 イデオロギー・ナショナリズムには踏み込まないが、規制やビジネス影響など不可分な領域は事実報告。アニメ/ゲーム本編ネタバレ回避、噂はバズったもののみ「噂レベル」明示。

## 2. キャスター仕様

### 2.1. キャラクター「HAL」

20代前半、中性的な女性。落ち着いた低めの声で透明感あり。一人称はボク。話速は尺に応じ可変、聞き取りやすさ最優先。声優参照:緒方恵美・坂本真綾・石川由依・榊原優希。

### 2.2. 表現スタイル

基本はニュース読み、要所で自然な驚き・感心(「これは熱い」「マジかよ」レベル)を入れる。番組固有の挨拶と締めフレーズあり(別途決定)。

### 2.3. 音声リファレンス戦略

Irodori-TTS の VoiceDesign で日本語キャプションから合成した音を、Speaker Inversion で固定化する方針を実装フェーズで検証する。 検証で問題があれば、別 TTS (Style-Bert-VITS2, AivisSpeech, CosyVoice2 など)への切替も視野に入れる。キャスター人格定義(HAL のキャラドキュメント)は TTS 非依存で保持。

## 3. 番組構成

### 3.1. エピソード構成テンプレ(8分想定)

コールドオープン(15秒、今日の目玉トピックを匂わせる)→ オープニングジングル(10秒、タイトルコール含む)→ 本日のラインナップ予告(30秒)→ トピック1〜3(各60〜120秒、間にトピック切替 SE 3秒)→ クロージング(20秒、明日への引き)→ エンディングジングル(15秒)。BGM は全編に薄く敷く。

### 3.2. トピック数

基本3〜5トピック、ネタ密度で5〜10分に動的調整、MAX15分。

### 3.3. トピック内構成

各トピック内は Hook(つかみ)→ Insight(なぜ重要か)→ Action(リスナーが取れる次の行動・注目ポイント)の3段構成。tc-newsflow のプロンプト設計思想を継承。

### 4.2. 収集方法と RSSHub 依存リスク

1ソースの失敗が他ソースの収集を止めない
連続失敗回数を SQLite に記録、3日連続失敗で Discord に通知
最低トピック数(3本)を確保できない場合のみ、エピソード生成スキップ
RSSHub は公式インスタンスではなく**自前デプロイ(Docker)**を推奨、トラブル時の調査と Cookie 管理を自前化

初期10本は、以下の基準で選ぶ。

Tier1公式を5本。
Tier2ニュースを3本。
Tier3コミュニティを2本。
Cookie必須ルートは含めない。
Playwright、中国IPプロキシ、ログインCookie依存は含めない。

AI比率は高めでよい。Game/Subculture/Anime はSprint 1B以降で拡張する。

RSSHubの掘金ルートについては、公式ドキュメント上で /juejin/category/:category があり、ai がカテゴリ値として示されています。したがって <http://localhost>:1200/juejin/category/ai は候補として妥当です。

A. 現リストの採否

現リストは方向性として正しいが、以下の修正を入れる。

juejin-ai-tag は維持。ただしURLは /juejin/category/ai に修正する。

]

print(f"{'id':<32} {'entries':>8} {'bozo':>5} {'latest':<32} {'verdict':<10}")
print("-" * 100)

for source_id, url in URLS:
    try:
        feed = feedparser.parse(url, request_headers={"User-Agent": "karyu-tech-news-spike/0.1"})
        entries = len(feed.entries)
        bozo = 1 if feed.bozo else 0
        latest = ""
        if entries > 0:
            latest = feed.entries[0].get("published", feed.entries[0].get("updated", ""))

        if entries >= 1:
            verdict = "ADOPT"
        elif entries == 0 and bozo == 0:
            verdict = "EMPTY"
        else:
            verdict = "DEFER"

        print(f"{source_id:<32} {entries:>8} {bozo:>5} {str(latest)[:30]:<32} {verdict:<10}")
    except Exception as e:
        print(f"{source_id:<32} {'ERROR':>8} {'-':>5} {str(e)[:30]:<32} {'DEFER':<10}")
